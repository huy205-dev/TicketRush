## Đã làm

- **Backend Redis** (`internal/inventory/redis.go`):
  - 3 script `hold.lua`, `release.lua`, `confirm.lua`, giữ đúng logic của SPEC 6.3–6.5, nhúng bằng `go:embed` và chạy qua `redis.Script`;
  - `Status` dùng `MGET` theo lô 500 key trong một pipeline;
  - chọn backend bằng `INVENTORY_BACKEND`, mặc định `redis`.
- **Sơ đồ ghế:** trả `version` lấy từ `seatmap:{eid}:version`; cache 500 ms và gzip giữ nguyên như M1.
- **Khoá idempotency** (quyết định trước M2, ADR-005):
  - `redisx.Locker` (`SET NX PX` với token ngẫu nhiên, nhả khoá bằng Lua so khớp token), dùng trong `order.Service.Create`;
  - request trùng đang chạy nhận `409 IDEMPOTENCY_KEY_IN_PROGRESS` kèm `Retry-After: 1`;
  - Redis không trả lời thì trả `503 SERVICE_UNAVAILABLE` kèm `Retry-After: 1` (fail closed).
- **Test tích hợp** trên Redis thật (testcontainers, helper `internal/platform/testredis`):
  - bộ test "hợp đồng" của inventory, gồm bài 1.000 goroutine một ghế và 200 goroutine × 2 ghế trong 20 ghế, chạy cho cả `pg` và `redis`;
  - test riêng cho từng script Lua: giữ, giữ lại cùng order, ghế đã bị chiếm, nhả sai chủ, confirm, version, `MGET` hơn 500 ghế;
  - test của order và test HTTP chạy cho cả hai backend, cùng các test mới cho khoá idempotency.
- **Đo tải:** `make bench-hold` với backend Redis còn so khớp toàn bộ key trong Redis với PostgreSQL sau mỗi lần (`loadtest/check_redis.sh`).

## Quyết định tự chọn

- **Nơi tăng `seatmap:{eid}:version`:** đặt trong backend Redis, ngay sau mỗi hold/release/confirm thành công. SPEC chỉ nêu bước này trong luồng tạo đơn, nhưng định nghĩa key là "tăng mỗi lần ghế đổi trạng thái". Không đưa `INCR` vào script, để giữ nguyên văn script của SPEC. `INCR` lỗi chỉ ghi log (ADR-001).
- **Đo lại PG ở commit M2** trước khi so sánh, để cả hai backend chạy cùng code. Từ M2, khoá idempotency nằm trên đường đi của mọi request tạo đơn, với cả hai backend.
- **Mã lỗi mới** `SERVICE_UNAVAILABLE` (503) cho trường hợp fail closed. SPEC không có mã nào cho tình huống này.
- **Khoá idempotency:** key `idem:<userId>:<key>`, TTL 30 s (dài hơn `WriteTimeout` 15 s của booking). Nhánh "vi phạm unique → tra lại" từ M1 được giữ làm lớp phòng thủ khi khoá hết hạn giữa chừng.
- `.env.example` trở lại mặc định `INVENTORY_BACKEND=redis` theo SPEC. Dòng `INVENTORY_BACKEND=pg` mà mình thêm vào `.env` local ở M1 cũng đã được bỏ.

## Hạn chế còn lại

- **p99 gần như không cải thiện** và cả hai backend đều chưa đạt mục tiêu (≥ 5.000 req/s, p99 < 200 ms). Giả thuyết, chưa kiểm chứng: mỗi request tạo đơn vẫn tra PostgreSQL theo Idempotency-Key, và dev-login ghi PostgreSQL ở mọi vòng lặp của k6, tất cả dùng chung pool 20 kết nối. Cộng thêm việc k6 tranh CPU trên cùng máy. Việc này để M7 điều tra.
- **Chưa có reconcile (M8).** Redis mất dữ liệu thì ghế đang giữ bị coi là trống trong Redis.
- **Chưa có expiry worker (M3).** Đơn `HELD` quá hạn vẫn `HELD` trong PostgreSQL, dù ghế trong Redis đã hết TTL.
- **Phụ thuộc Redis:** API tạo đơn cần Redis kể cả với backend `pg`, vì khoá idempotency dùng Redis.
